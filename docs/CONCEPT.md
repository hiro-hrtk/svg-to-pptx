# svg-to-pptx — コンセプト・設計仕様

## 背景・目的

アーキテクチャ図・インフォグラフィックなどのSVGファイルを、**PowerPointのネイティブオブジェクト**(図形・コネクタ・テキストボックス)に変換する。

単純にSVGをレンダリングしてPNGとして貼り付けるだけなら簡単だが、それでは:
- スライド上でテキストの編集・修正ができない
- 図形の色や位置を後から調整できない
- 文字の再利用(検索・翻訳・アクセシビリティ)ができない

という制約が残る。本プロジェクトは、SVGの図形要素をPPTXの図形・コネクタに、`<text>` をPPTXのテキストボックスに変換し、**PowerPoint上で完全に編集可能なスライド**を生成することを目指す。

> 本ドキュメントは元プロジェクト(旧称 svg_to_pptx_native)のスキル・ドキュメント一式が消失した後、
> `REF/` に復旧できた断片(SKILL.md / CLAUDE.md / CONCEPT.md / ARCHITECTURE.md / DECISIONS.md / config.yaml / test-check-list.md)
> をもとに再構築したものである。再構築にあたり、アイコン・曲線パス・装飾線を多用したインフォグラフィックの
> テストSVGをテストケースとして、対応要素を拡張している(詳細は後述)。

## 入力の想定

SVGは以下の2パターンに対応する。

1. **単一SVGファイル**: 図形とテキストが混在する通常のSVG
2. **no_text / text_only ペア**: 同じ図を「テキストなし版」と「テキストのみ版」に分割したもの

どちらのパターンでも、`svg_elements.py` が `no_text` 相当を図形として、`text_only` 相当をテキストとしてパースする
(単一SVGの場合は同じファイルを両方の引数に渡せばよい。`parse_shapes()` は `<text>` を無視し、`parse_texts()` は `<text>` のみを見るため、
同じファイルを渡しても図形とテキストは正しく分離される)。

## 対応SVG要素

| 要素 | PPTX変換先 | 備考 |
|------|-----------|------|
| `<rect>` | Rectangle / RoundedRectangle | `rx`/`ry`>0で角丸。`adj = rx / min(w,h)` |
| `<circle>` `<ellipse>` | Oval | |
| `<line>` | Straight Connector | `marker-end`があれば矢じりを追加描画 |
| `<polyline>` `<polygon>` | Freeform(開放/閉合) | polygonのみ塗り対象 |
| `<path>` | Freeform(サンプリング近似) | 下記参照。`marker-end`対応 |
| `<image>` (base64) | Picture | |
| `<text>`(`<tspan>`込み) | TextBox | マッピング・concat・fit_textを経て配置 |

## スタイルの解決(CSS簡易対応)

SVG生成ツールによっては、属性を直接書かず`<style>`内のクラスセレクタ(`.title { font-size:38px; }`)で
スタイルを与えることがある。本パイプラインは単純なクラスセレクタのみサポートする
(結合子・疑似クラス・idセレクタ・カスケード詳細度計算は非対応)。解決優先順位は
**inline style属性 > CSSクラス(スタイルシート記述順で後勝ち) > 直接属性 > デフォルト値**。

## SVG標準マーカー(矢じり)対応

`marker-end="url(#id)"` と `<defs><marker>...</marker></defs>` の組み合わせ(`orient="auto"`,
`markerUnits="strokeWidth"`)に対応する。マーカー内の`<path>`/`<polygon>`形状を、線・pathの
終点の位置・向き(進行方向)に合わせて配置し、塗りつぶしFreeformとして追加描画する
(元のSVGが矢じりを`<polygon>`で個別に描画している場合は、この仕組みを使わずそのまま
`<polygon>`として変換される)。

### `<path>` の扱い

`M/m L/l H/h V/v C/c Q/q A/a Z/z` の主要コマンドに対応し、ベジエ曲線・楕円弧を折れ線サンプリングして
Freeformで近似する(`svg_elements.parse_path_d`)。閉じたpath(`Z`で終わる、かつfillあり)は塗りつぶし対象、
開いたpathは線のみとして描画する。

## コアコンセプト

### 1. 図形はSVG要素→PPTX図形に直接変換する

色・線幅・破線(`stroke-dasharray`)・要素の`opacity`もできる限り再現する。`fill="url(#grad)"` のような
グラデーション参照は、gradientの各stop色を平均した単色で近似する(PPTX側でも真のグラデーションは表現可能だが、
実装コストとのバランスから単色近似を採用)。

### 2. テキストは「所属する図形」にマッピングし、独立したテキストボックスにする

各 `<text>` 要素について、それを内包する最小の矩形(`rect`/`image`)を探す(`mapping.py`)。
内包する図形が見つからない場合は、最近傍の矩形にフォールバックするが、**フォールバックは「真の内包」とは
区別して扱う**(`contained` フラグ)。

キャンバス全面を覆う背景矩形(`rect`の幅・高さがSVG全体の90%以上)は、内包判定の対象から除外する
(除外しないと、ほぼ全てのテキストがこの巨大矩形に「内包」されてしまい、本来のフォールバック判定が機能しない。
ADR-007参照)。

円・楕円・線・pathなどの装飾図形は「内包コンテナ」の候補にしない(元々rectのみを想定した設計方針を踏襲)。

### 3. 隣接するテキストは意味のまとまりでconcatする

同じ矩形に所属し、縦方向・横方向の両方で近接するテキスト要素は、1つのテキストボックス(複数paragraph)に
まとめる(`concat_text.py`)。横方向の近接も必須条件にすることで、無関係な浮遊ラベル同士の誤結合を防ぐ。

大面積コンテナ(`container_area_threshold_px2`)はconcat対象外(外枠にフォールバックした複数の無関係な
浮遊テキストが誤って1つに結合されるのを防ぐ)。

### 4. 位置決めの大原則:「テキストは常に自分自身の元の座標を信頼する」

これが最大の設計原則であり、開発中に見つかったバグの根本原因は**この原則を破っていたこと**だった。

- ❌ NG: 所属する図形(shape)の中央・端を使ってテキストの位置を決める
- ✅ OK: テキスト自身の元のx,y座標(text-anchor込み)を使って位置を決める。図形は「折り返しに使ってよい幅
  (content_width)」を提供するだけ

```
anchor='start'  → box_l = anchor_x
anchor='middle' → box_l = anchor_x - content_width/2
anchor='end'    → box_l = anchor_x - content_width
```

縦位置は常に `block.top`(テキスト自身の元位置)を使う。ただし例外として、**元は1行のテキストだったが
収まりきらずfit_text側で複数行に折り返された場合のみ**、コンテナ内で縦中央揃えに補正する(ADR-009)。
これは「複数行への折り返し」自体がconcatによる元々の設計ではなく、パイプライン側で新たに発生させた
レイアウト変化であるため、`block.top`基準のままだとコンテナから明確にはみ出してしまうことへの対処である。

### 5. フォントサイズは実測メトリクスでフィットさせる

Meiryo UIフォント(`C:/Windows/Fonts/meiryo.ttc`, index=2)をPILで読み込み、実際の文字幅を測定して
折り返し計算・フォントサイズ自動縮小を行う(`fit_text.py`)。縮小は所属図形の高さに収まるまで比率を
保ったまま行う。

meiryo.ttcにはUI Bold書体が無いため、太字はPPTX側の`font.bold=True`による疑似ボールドで表現する。
疑似ボールドはRegular書体の実測幅より広くレンダリングされるため、太字テキストの幅測定には安全係数
(`_BOLD_WIDTH_FACTOR=1.12`)を掛けて折り返し判定を安全側に倒す(ADR-008)。

### 6. 浮遊テキストは不透明背景で「線を隠す」

元のSVGは、線の上にテキストを乗せる際に `<mask>` で線に穴を開けて見せている場合がある。PPTX変換では
このマスクを解釈せず、代わりに**内包されていない(浮遊)テキストボックスに不透明な背景色を敷く**ことで、
視覚的に同じ効果を再現する。

ただし、**近傍に図形が全く見つからない完全に孤立したテキスト(タイトル・キャプション等)には白背景を
敷かない**(ADR-010)。何も隠す必要のない孤立テキストにまで背景箱を敷くと、無地の背景の上に不要な
矩形が目立ってしまうため。

## アーキテクチャ

```
code/
├── svg_elements.py    SVGパース。ShapeElem(図形) / TextElem(テキスト) に正規化
├── mapping.py          テキスト→所属図形のマッピング(真の内包 / フォールバック区別)
├── concat_text.py      隣接テキストのconcat(縦近接 かつ 横近接)、TextBlock生成
├── fit_text.py          PIL実測メトリクスでの折り返し・フォントサイズ自動フィット
├── build_pptx.py       全体の変換パイプライン本体。図形変換・テキスト配置・PPTX生成
├── qa_capture.py        PowerPoint COMでスライドをPNGにエクスポート(視覚QA用)
└── config.yaml          フォント・レイアウト・マッピング閾値等の設定
```

### データフロー

```
no_text.svg ──→ parse_shapes() ──────────────────────→ ShapeElem[]
text_only.svg ─→ parse_texts() ─→ TextElem[]
                                        │
ShapeElem[] + TextElem[] ──→ build_mapping() ──→ {text_id: shape_id}, contained_ids
                                        │
                          build_text_blocks() ──→ TextBlock[] (concat済み)
                                        │
                          fit_block() (各blockごとにフォント自動フィット, PIL実測px)
                                        │
                          build() ──→ PPTX (図形→テキストの順で描画)
                                        │
                          qa_capture.export_slide_png() ──→ 視覚QA用PNG
```

## QAサイクル

1. `build_pptx.py` でPPTXを生成
2. `qa_capture.py` でPowerPoint COM経由でスライドをPNGエクスポート
3. PNGを視覚確認し、問題箇所を特定
4. `output/<session>/*_mapping.json`(テキスト→図形のマッピング表)と突き合わせて原因を特定
5. 該当モジュールを修正し、1に戻る

## 既知の制約・今後の検討事項(追記: 2件目のテストケースで判明)

- **アイコン画像に文言が焼き込まれている場合の重複**: SVG生成ツールによっては、アイコン画像
  (base64埋め込みPNG等)自体に既にラベル文字が描画されており、かつ同じラベルを表す独立した
  `<text>`要素も別途重ねて配置されていることがある。本パイプラインは画像の中身(ピクセル)を
  解釈しないため、この場合は画像側のラベルとPPTX側のテキストボックスが二重に表示される。
  これは入力SVG側の重複であり、パイプラインが自動判定して片方を省略することはしない
  (どちらが不要かを一般的に判定する手段が無いため)。気になる場合は生成元のSVGを見直すか、
  変換後にPowerPoint上で該当テキストボックスを削除する。
- **CSSは簡易対応のみ**: 結合子・疑似クラス・idセレクタ等は非対応(前述)。
- **`<filter>`(dropshadowなど)は非対応**: `filter="url(#...)"` は無視され、影などの視覚効果は
  再現されない。

## 既知の制約・今後の検討事項

- **z-order(重なり順)は「図形→テキスト」に固定**しており、元SVGの本来の描画順(テキストの後に描画される
  図形がテキストより手前に来る等)までは再現しない。密集したアイコン+ラベルが近接している場合、本来は
  ラベルの後ろに隠れるはずの装飾線がラベルに重なって見えることがある(例: あるラベルと近接する
  アイコンの円弧が重なって見えるケース)。
- **SVGにはテキストの行間(line-height)という概念が無い**(各`<text>`は独立した絶対配置のベースライン)のに対し、
  PPTXのテキストボックスは常にフォント内部メトリクス由来の行box(line box)を持つ。元SVGが視覚的密度を優先して
  極めて狭い行間(例: 16px相当のフォントに対し14px間隔)で独立した複数の`<text>`を配置している場合、
  PPTX側では行box同士がわずかに重なって見えることがある(フォントメトリクス起因で完全には解消できない)。
- **Bezier曲線・楕円弧**: `<path>` はサンプリングによる折れ線近似のため、極端に長い曲線区間ではわずかに
  角張って見えることがある。
- **フォント**: Meiryo UI固定。他フォントを使う場合は `config.yaml` の `font.font_file` / `font_file_index` を
  変更する必要がある。
- **グラデーション**: 単色近似(stop色の平均)。
